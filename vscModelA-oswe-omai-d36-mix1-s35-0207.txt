User: # TITLE - Databricks Identifier/Keyword Handling Regression (Multiple Keywords as Identifiers)

## [Problem Statement]
You are working on a lightweight SQL parsing module that supports a small subset of Databricks DDL. A user reported that parsing Databricks SQL fails when using certain words (like `interval`, `comment`, `struct`) as identifiers without backticks, even though Databricks documentation indicates these are not reserved keywords under ANSI compliance and should be usable as identifiers in appropriate contexts.

The parser currently supports `CREATE TABLE ... ( col STRUCT<...> )` and optional `COMMENT '...'` on struct fields. However, a systematic regression/bug causes the parser to incorrectly treat context-dependent keywords as globally reserved, breaking valid Databricks SQL.

### Specific Bug Manifestations

The following 6 related bugs have been identified:

**Bug 1-3 (Tokenizer Level)**: Words incorrectly categorized as globally reserved keywords
- `INTERVAL` is in the KEYWORDS set but should be usable as an identifier
- `COMMENT` is in the KEYWORDS set but should be usable as an identifier (contextual keyword)
- `STRUCT` is in the KEYWORDS set but should be usable as an identifier (contextual keyword)

**Bug 4-6 (Parser Level)**: Parser strictly requires IDENT tokens in identifier positions, rejecting KW tokens
- Table names: Parser rejects keywords as table names
- Column names: Parser rejects keywords as column names  
- Struct field names: Parser rejects keywords as struct field names

Your task is to fix these functional bugs so that the parser behaves as Databricks specifies.

## [Requirements]

### Functional Requirements

1) **Databricks mode fix**: In `read="databricks"` mode, the following must parse successfully:
   - `CREATE TABLE interval (col STRUCT<foo: INT>)` — keyword as table name
   - `CREATE TABLE t (interval STRUCT<foo: INT>)` — keyword as column name
   - `CREATE TABLE t (col STRUCT<interval: DOUBLE>)` — keyword as struct field name
   - `CREATE TABLE t (col STRUCT<comment: STRING>)` — keyword as struct field name
   - `CREATE TABLE t (col STRUCT<struct: INT>)` — keyword as struct field name
   - `CREATE TABLE t (col STRUCT<interval: DOUBLE COMMENT 'description'>)` — with COMMENT clause

2) **Keep quoted identifiers working**: The following must still parse correctly:
   - `CREATE TABLE `interval` (col STRUCT<foo: INT>)`
   - `CREATE TABLE t (`interval` STRUCT<foo: INT>)`
   - `CREATE TABLE t (col STRUCT<`interval`: DOUBLE>)`
   - `CREATE TABLE t (col STRUCT<`interval`: DOUBLE COMMENT 'aaa'>)`

3) **Do not relax invalid syntax**: Clearly invalid struct definitions must still fail:
   - Missing `:` in struct field definition
   - Missing `>` to close struct
   - Missing type after `:`
   - Other syntactically invalid constructs

4) **Preserve API**: Keep the public entrypoint `parse_one(sql: str, read: str = "databricks") -> CreateTable`

5) **Regression tests**: Add comprehensive tests proving:
   - All 6 bugs are fixed (unquoted keywords work as identifiers)
   - Quoted identifiers still work
   - Invalid syntax still fails appropriately

### Non-Functional Requirements

- Make changes minimal and localized
- No new dependencies beyond test tooling
- Keep code readable and consistent with existing style
- Maintain backward compatibility for valid syntax

   - Fix tokenizer to handle context-dependent keywords appropriately

   - Invalid struct syntax cases (should fail appropriately)

3. **Documentation**:
   - Short note explaining what changed and why

## [Scope & Constraints]

### In Scope

- Parser behavior: Accepting keywords in identifier positions (table names, column names, struct field names)
- Databricks dialect handling and ANSI compliance
- Comment parsing on struct fields

### Out of Scope
- Full SQL dialect coverage beyond provided subset
- Full Databricks grammar beyond CREATE TABLE with STRUCT
- Nested complex types beyond what base code already supports
